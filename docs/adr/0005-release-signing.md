# ADR 0005: Release signing with minisign (Ed25519)

- Status: Accepted
- Date: 2026-10-23

## Context

Decision D-04 and the specification (9.8, ORB-REL-003, AT-013) require releases signed with an Ed25519-based key, preferably Minisign-compatible, so that installer and updater do not trust HTTPS or a hash from the same download source alone. D-D03 left the concrete implementation open for Gate G2. Constraints: no secret in the repository, no long-lived credentials on the target (D-C13), minimal dependencies, verification must later work on a small device without a network service other than the release download.

## Decision

1. **Tool:** [minisign](https://github.com/jedisct1/minisign) 0.12, the reference implementation of the Minisign format. CI installs the upstream static Linux release with `scripts/install-minisign.sh`, pinned by version and SHA-256 (`9a599b48ba6eb7b1e80f12f36b94ceca7c00b7a5173c95c3efc88d9822957e73`). The pinned checksum was computed after verifying the archive's `.minisig` against the upstream public key `RWQf6LRCGA9i53mlYecO4IzT51TGPpvWucNSCh1CBM0QTaLn73Y7GFO3` (listed in the upstream README). It is the only new tool in the release path. No GitHub Action is used for it.
2. **What is signed:** only `checksums.txt`, as `checksums.txt.sig` (`minisign -S -x checksums.txt.sig`). `checksums.txt` lists the SHA-256 of the bundle, `manifest.json` and the SBOM files in `sha256sum` format. The manifest repeats the bundle hash, and a verifier checks both. A trusted comment (`oarfish <tag> <commit>`) is part of the signature.
3. **Key:** one dedicated release key pair, generated by the maintainer on their machine with `minisign -G -W`. The private key lives only in the GitHub Actions secret `OARFISH_RELEASE_SIGNING_KEY`, which the workflow reads in a single step of the `sign` job. The repository contains only the public key, `release/oarfish-release.pub`. The key is unencrypted (`-W`) because a password stored in a second secret next to the key would add no protection and would add a failure mode in CI. The protection is the secret store, an offline backup in a password manager, and restricting who can push tags.
4. **Workflow shape:** `build` (no secrets) → `sign` (the only job that references the secret, read-only token; it only starts for a tag push, so pull-request and manual dry runs, which use `sign-dry-run` with a throwaway key, never receive it) → `publish` (the only job with `contents: write`, no secret). `sign` verifies with the committed public key; `publish` verifies again after the artifact handoff.
5. **Tests:** `scripts/test-signing.sh` runs on every CI run and in the release workflow. It uses throwaway keys generated inside the test and checks that a tampered `checksums.txt`, bundle, manifest, SBOM or signature, a missing signature, a signature from another key and a signature replayed from another release are all rejected, each for the expected reason. Dry runs sign with a throwaway key through the same scripts.
6. **Format:** minisign legacy mode (`minisign -S -l`, algorithm id `Ed`): a plain Ed25519 signature over the bytes of `checksums.txt`. See "Amendment" below, which supersedes the earlier choice of the default prehashed mode (`ED`).

## Alternatives considered

- **cosign / Sigstore keyless:** needs OIDC identity, a transparency log and network access to verify, and a larger verifier on the device. Rejected for the offline, pull-based installer path.
- **GPG:** large, complex trust model, poor fit for an embedded single key.
- **signify (OpenBSD):** same idea, less common tooling on developer machines and runners.
- **Own signer and verifier in Go:** would avoid a binary but means writing and maintaining security-critical code. Not needed for G2.

## Consequences

- The public key is embedded later, not in this gate: the installer (G3) carries the one-line key text; the Oarfish updater (G6) embeds the same file with `go:embed`. `release/oarfish-release.pub` is the single source. Installer and updater must verify `checksums.txt.sig`, then the hashes, and must not rely on HTTPS alone.
- **Open point for G3 and G6, not decided here:** key rotation and revocation are not designed. Losing the private key means devices that embed only this public key cannot accept new releases without a new installer.
- Releases cannot be published without the secret and the committed public key; the workflow fails explicitly if either is missing.
- GitHub Actions secrets are readable by any workflow run on a tag that a maintainer with write access can create. Tag protection or a deployment environment with required reviewers would narrow this. That is recommended in `docs/RELEASING.md` and not configured by this gate.

## Amendment: legacy mode instead of prehashed mode (2026-10-23, before the first release)

This supersedes the first version of decision 6 in this ADR, which used minisign's default prehashed mode. No release had been published at that point, so nothing was signed in that format.

- **Reason:** only the small `checksums.txt` is signed. Minisign's default mode hashes the message with BLAKE2b-512 before signing, which is meant for large files and would force the updater to depend on `golang.org/x/crypto/blake2b` and the installer to find a BLAKE2b implementation. For a message of a few hundred bytes the prehash adds nothing, and legacy mode keeps the same Ed25519 security. A legacy signature is verified with Go's `crypto/ed25519` alone (`scripts/bundlegen/ed25519_test.go` does exactly that against a signature produced by `scripts/sign-release.sh`), so the updater needs no extra dependency.
- **Layout of the files** (both are minisign text files; the second line is base64): public key = `Ed` (2 bytes) + key id (8) + Ed25519 public key (32); signature = `Ed` (2) + key id (8) + Ed25519 signature (64). The signed message is the exact content of `checksums.txt`. The trusted comment has its own global signature; a verifier that wants to trust the comment must check it too, otherwise it must ignore it.
- **Enforcement:** `scripts/sign-release.sh` passes `-l`. `scripts/verify-release.sh` rejects any signature whose algorithm id is not `Ed`, and `scripts/test-signing.sh` checks that a valid prehashed signature from the trusted key is refused.
- **The signature format is fixed once `v0.1.0-alpha.1` is published.** Installers and updaters will be written against it. Changing it later means a new installer, so `-l` must not be removed afterwards.
- **Remaining cost:** minisign-the-tool still verifies both formats, so `minisign -V` alone does not enforce the format; the repository script does.
