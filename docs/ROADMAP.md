| G5.1 | Local access control and audit foundation. Scope per [ADR 0009](adr/0009-local-access-control-and-audit.md) (D-C45 to D-C48): Argon2id password hash, in-memory sessions, strict cookie and CSRF protection, setup token for the first account, rate limiting, own audit file, every `/api/v1` route behind a session; loopback only. Exit: state-changing endpoints reject requests without a valid session and without CSRF protection; audit entries contain no secrets; login verified on the Raspberry Pi. Also measured on the Pi: the password hash benchmark and the audit write load. Status: implemented and tested ([`AUTH.md`](AUTH.md)); the Raspberry Pi evidence (reference device, `v0.1.0-alpha.6`) was reviewed and G5.1 passed on 2026-11-02, with one open observation (an unexplained audit entry, see [`AUTH.md`](AUTH.md#open-observations-from-the-device-run)) |
| G6 | GUI self-update, verification, health check, and rollback; Update Helper as a separate privileged process. G6 closes only after G6.10 is accepted |
| G6.0 | Design stop: ADR 0010 accepted with the owner decisions, decisions recorded, specification 0.3.5, ADR 0009 amendment A6. Documentation only. Stop point: the owner says "merge" for the documentation pull request |

Stop point: the owner confirms or changes the hardening and the unit layout from the findings |
| G6.2 | Release tooling: bundle contract (helper binary and unit files), additive manifest fields, `bundlegen` checks and tests. Stop point: green dry-run release |

| G6.8 | Update page (Svelte). Stop point: the owner reviews the UI. Status: implemented with jsdom tests, reference screenshots and a development scenario mode ([`UI.md`](UI.md#update-page-step-g68), ADR 0010 A12); the fix C2 of the G6.7 review is part of it. Done: PR #36 (merged). The page was exercised in the G6.9 device run through the GUI update and the GUI texts (observed on one device, [`UPDATE.md`](UPDATE.md#results-on-the-reference-device)); the page now has the second confirmation dialog (G6.10 step c, class C tests with jsdom); it has not been exercised on a device |
| G6.9 | Hardware evidence for the base update on the reference device, and documentation. Stop point: the owner reviews the evidence; G6 stays open. Status: the device evidence was collected on the reference device (class D and T, observed on one device, nothing Verified; [`UPDATE.md`](UPDATE.md#results-on-the-reference-device)). The bootstrap releases `v0.1.0-alpha.7` to `v0.1.0-alpha.10` were published. Follow-up from the first device evidence: the boot order of the recover unit was corrected (ADR 0010 A14, D-C81; PR #41); the corrected unit ran on the reference device and the boot check was observed as expected (class D, `v0.1.0-alpha.10`). Open items (journal search of the controlled boot, C3, retention of failed releases) are listed in the results section of `UPDATE.md`. G6 stays open until G6.10. Stop point: the owner decides whether G6 passes. Delivered in three implementation steps, each with its own session and pull request, followed by a release and the device evidence (ADR 0010 A15, D-C83). Status: **steps a to c are merged, implemented with class C tests (fake root, fake systemd, the fake helper, jsdom); nothing of it ran on a device, and no release carries it.** Step a: the owner decisions D1 to D7 (A15, D-C83) and the unit lint. Merged: PR #44 (merge commit `ee25caa`). PR #45 (merge commit `857b481`, Go 1.27.4 toolchain) is a separate task and not part of G6.10. Step c: the owner decisions F1 to F5 (A17, the addition to D-C84): the second confirmation that names the components, the texts of every result and installer case in German and English, the discard after a refused `activate`, the last result of a rebuilt state, the hand-over of the helper shown as progress within 60 seconds, the scenario mode and the closing documentation (`UPDATE.md`, `UI.md`, `INSTALL.md`, `RELEASING.md`, `DEVELOPMENT.md`); the remediation G1 and G2 (A17.5, the addition to D-C84): the second confirmation cannot be skipped, and the test helper `settle()` no longer races. Open: (1) the release that carries the helper of step b (one installer run on every device); (2) device evidence of the failure rows F24 to F32 (class D and T), including F24 on a second real release; (3) the closeout list of the failure matrix U13; (4) the owner's decision whether G6 passes. | (task) N0 | Default route and DNS display (ORB-NET-001, D-C72). Known sources (device observation, ADR 0008 amendment after S1): the default rows of `/proc/net/route` and `/proc/net/ipv6_route`, and `/etc/resolv.conf`; adding them to the read allow-list is a proposal of the amendment and is done in this task, with a test on the device under the unit hardening; images with a resolver stub need a fallback design (not tested). Implementation order after G8: G10, then G9, then G11; the identifiers stay unchanged (D-C75).

Reserve, which may follow the MVP acceptance (D-C69): the journal view and the process view (ORB-LOG-001 is SOLL, ORB-PRC-001). Later and not part of this plan: throttling and undervoltage warnings (ORB-DASH-004, task T1). Device observation from S1: undervoltage is readable from the `rpi_volt` hwmon alarm file (whether it is live or latched is not checked); a frequency cap is not available as a flag.

The standing rules for the implementation agent are in [`AGENT_RULES.md`](AGENT_RULES.md) (D-C79); a gate prompt says to read that file first and adds only the scope of the gate. Updating the status line of a gate or task in this table is part of its definition of done.

Each gate receives its own prompt for the implementation agent. A later gate must not be implemented early unless the specification is formally changed.
